# P1 · Credencial por defecto postgres/12345 escrita en la BD del core al instalar

> Severidad de la auditoría: **Alta**. Este documento PRUEBA que el riesgo es tangible y lo
> fundamenta en marcos reconocidos. No es una PoC: es trazabilidad probatoria y material formativo
> para el equipo.

## Dónde vive

En dos puntos del código, que juntos fijan la credencial de la conexión a la BD externa
`integracion`:

- `settings.php:33-34` declara el ajuste con un DEFAULT literal:
  `admin_setting_configpasswordunmask('local_portafolio/integracion_dbpass', …, '', '12345')`.
- `classes/infrastructure/IntegracionDbConnection.php:45` fija el usuario por defecto:
  `get_config('local_portafolio','integracion_dbuser') ?: 'postgres'` — el **superusuario** del
  cluster, para una conexión que la propia clase documenta como «de solo lectura».

Y, sobre todo, en el EFECTO del instalador: al correr `admin/cli/upgrade.php` (§14.3b del DEPLOY.md),
esos defaults se escribieron **en la base de datos del core** sin intervención. Verificado tras el
despliegue de esta auditoría (2026-08-25):

```
mdl_config_plugins:
  local_portafolio | integracion_dbuser | postgres
  local_portafolio | integracion_dbpass | 12345
```

## Por qué es tangible

- **El default se materializa solo.** No hace falta que nadie escriba `12345`: el `install.php`
  lo persiste al instalar. Un despliegue que no pase MANUALMENTE por la UI (Administración →
  Plugins → Portafolio) queda con `postgres`/`12345` como credencial activa de la réplica.
- **La contraseña es trivial y el usuario es superusuario.** `postgres` no es un rol de lectura:
  puede crear, borrar y alterar cualquier BD del cluster. Si la réplica `integracion` vive en el
  MISMO PostgreSQL que el Moodle principal (que es el caso en este ambiente, y el manual §6.2/§8.2
  lo contempla), esa credencial da acceso de superusuario a la BD `moodle` entera.
- **Cadena, con evidencia de esta auditoría:** el despliegue siguiendo el manual dejó `12345`
  en `mdl_config_plugins`; cualquiera con acceso de lectura a esa tabla (un admin de otro plugin,
  un backup mal protegido) obtiene una contraseña de superusuario de PostgreSQL en claro.
- **El propio manual lo llama «placeholder de desarrollo, no usar con datos reales» (§6.2)** — pero
  el placeholder viaja en el código y es el valor efectivo si nadie lo cambia. Documentar el riesgo
  no lo elimina.

**Contramedida demostrada en esta auditoría:** el despliegue local se corrigió a un rol dedicado de
solo lectura (`portafolio_integ_ro`), verificado con SELECT pero SIN privilegio de escritura
(`INSERT → permiso denegado`). Es la forma correcta, y prueba que el default es evitable.

## OWASP

- **A05:2021 Security Misconfiguration** — el ejemplo canónico de la categoría es «cuentas y
  contraseñas por defecto sin cambiar». Encaja exacto.
- **A07:2021 Identification and Authentication Failures** (secundaria): uso de una credencial
  débil y conocida (`12345`) para autenticar contra la BD.
- **WSTG-CONF-06** (Test for default credentials) y **WSTG-ATHN-02** (Testing for Default
  Credentials): los procedimientos que confirman este hallazgo.
- **ASVS v4.0 — 2.10.4**: «los secretos por defecto del sistema deben cambiarse»; y **1.4.4**:
  usar el mínimo privilegio. Incumplidos: `postgres` es el máximo privilegio.

## MITRE

- **CWE-1188: Initialization of a Resource with an Insecure Default** — la debilidad exacta: el
  recurso (la conexión) se inicializa con un valor por defecto inseguro.
- **CWE-798: Use of Hard-coded Credentials** — la contraseña vive en el código fuente.
- **CWE-269: Improper Privilege Management** — usar `postgres` (superusuario) para una conexión de
  solo lectura viola el mínimo privilegio.
- **ATT&CK T1078.001 Valid Accounts: Default Accounts** — la técnica del adversario: usar cuentas
  por defecto para acceder. Secundariamente **T1552.001 Unsecured Credentials: Credentials In
  Files** (la contraseña en el código / en `mdl_config_plugins`).

## STRIDE

**Elevation of Privilege**: una credencial de superusuario por defecto permite escalar de «acceso
a la config de un plugin» a «control total de la BD del cluster». Secundariamente **Information
Disclosure**: la contraseña queda legible en claro en el código y en `mdl_config_plugins`.

## CVSS

**CVSS 3.1: 8.8 (Alta)** — `AV:N/AC:L/PR:L/UI:N/S:C/C:H/I:H/A:H`. Un atacante con privilegio bajo
(lectura de la config del plugin) obtiene una credencial de superusuario que compromete
confidencialidad, integridad y disponibilidad de la BD; Scope Changed porque el impacto cruza del
plugin a todo el cluster PostgreSQL. `PR:L` porque hay que poder leer `mdl_config_plugins` o el
código desplegado.

## ISO/IEC 27001

- **A.5.17 Información de autenticación** — la gestión de credenciales por defecto/débiles.
- **A.8.24 Uso de criptografía / gestión de secretos** — un secreto en claro y por defecto.
- **A.8.2 Derechos de acceso privilegiado** — el uso de superusuario donde basta lectura.
- **A.8.9 Gestión de configuración** — la configuración segura del despliegue.

## Qué debe asimilar el equipo

Un valor por defecto en el código NO es una sugerencia: es el valor de producción para todo el que
no lo cambie a mano, y los instaladores automáticos nunca lo cambian. Dos reglas: (1) la credencial
de una conexión de solo lectura debe ser un rol de solo lectura, nunca `postgres`; (2) un ajuste
sensible sin default seguro debería quedar VACÍO y hacer fallar el plugin con un mensaje claro
(«configura la BD de integración»), no arrancar con `12345`. Fallar cerrado enseña; arrancar con un
default débil esconde.

## Criterio de cierre

`settings.php` no trae `'12345'` como argumento por defecto del ajuste de contraseña (default
vacío), y `IntegracionDbConnection` no cae a `'postgres'` como usuario; o, en su defecto, el
despliegue documenta y obliga a un rol de solo lectura. Verificable: `grep -n "12345\|'postgres'"`
en esos dos ficheros no devuelve la credencial, y `mdl_config_plugins` no contiene `12345` tras un
`install.php` limpio.

## Qué está pasando

El despliegue del equipo en `zajunavideo5` publica el origen Apache **sin TLS** en el puerto 8000.
`https://zajunavideo5.com/api/` (con barra final) responde 301 a `http://zajunavideo5.com:8000/api`,
y ese puerto sirve la API ENTERA en claro: `/api/contact-info` → 200 JSON, `/api/surveys` → 401,
y `/api/login` PROCESA autenticación (comprobado con credenciales falsas; las reales no se mandan
por un canal sin cifrar).

## Por qué es un riesgo

Cualquiera en la red entre el cliente y el servidor puede leer —o modificar— el tráfico: en
particular, la contraseña de un usuario que inicie sesión contra el 8000. El
`Strict-Transport-Security` que el propio 8000 devuelve es decorativo: un navegador ignora HSTS
cuando la respuesta llega por HTTP. Es un canal de robo de credenciales abierto de par en par.

## Recomendación de remediación

Cerrar el puerto 8000 al exterior (que solo el proxy inverso hable con Apache, por la red interna)
o, si debe quedar expuesto, terminar TLS también ahí y redirigir todo HTTP a HTTPS. El backend no
debe ser alcanzable en claro desde fuera del host.

## Verificación

`curl -s -o /dev/null -w "%{http_code}" http://zajunavideo5.com:8000/api/contact-info` debe pasar
de 200 a conexión rechazada (o 301→https). El spec `encuestas-mecanismos.spec.ts` («el puerto 8000
NO debería servir la API en HTTP plano») pasará a verde cuando se corrija.

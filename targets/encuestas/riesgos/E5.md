# E5 · PgBouncer: arranque circular no documentado + userlist.txt sin gitignore

> Severidad de la auditoría: **Media**. Documento probatorio y formativo.

## Dónde vive

`deploy/pgbouncer/userlist.txt` (y su `.example`), `deploy/pgbouncer/pgbouncer.ini`
(`auth_type = scram-sha-256`, `auth_file = /etc/pgbouncer/userlist.txt`) y el `.gitignore` del
repositorio `encuestas_backend`.

## Por qué es tangible

Dos problemas distintos, ambos verificados en el despliegue local (2026-08-24):
- **(a) Dependencia circular no documentada:** el `userlist.txt` necesita el hash SCRAM del rol
  `encuestas`, que **solo existe después** de que el contenedor `postgres` cree el rol al primer
  arranque; pero `pgbouncer` monta `userlist.txt` al arrancar (`depends_on: postgres healthy`). En
  un despliegue desde cero, el fichero no puede tener el hash correcto todavía. Orden real
  necesario (que el manual no da): levantar `postgres` solo → leer `pg_authid.rolpassword` →
  escribir `userlist.txt` → levantar el resto. Es una fricción de disponibilidad.
- **(b) Fichero de credenciales sin proteger:** el `.gitignore` NO cubre
  `deploy/pgbouncer/userlist.txt` (solo ignora `.env*`), pese a que el README §1 dice «NO versionar
  el real». Nada impide versionar el hash SCRAM de la BD de producción.

## OWASP

- **A05:2021 Security Misconfiguration**: procedimiento de arranque incompleto (a) y control de
  versiones que no protege un fichero de credenciales (b).
- **A02:2021 Cryptographic Failures** para (b): riesgo de exponer un verificador de credenciales.
- **ASVS v4.0 — 14.1.1** (build/despliegue reproducible) para (a); **6.4.1** (secretos fuera del
  repo) para (b).

## MITRE

- (a) **CWE-665: Improper Initialization** — orden de inicialización de recursos con una dependencia
  circular no resuelta.
- (b) **CWE-522: Insufficiently Protected Credentials** y **CWE-538: Insertion of Sensitive
  Information into Externally-Accessible File**. ATT&CK **T1552.001** si el hash se versiona.

## STRIDE

(a) **Denial of Service** (el arranque se atasca). (b) **Information Disclosure** → **Spoofing**
(un hash SCRAM versionado permite montar un PgBouncer que suplanta al legítimo, o crackear offline).

## CVSS

Parte (b): **CVSS 3.1: 4.3 (Media)** — `AV:N/AC:L/PR:L/UI:N/S:U/C:L/I:N/A:N` (requiere acceso al repo;
el hash SCRAM no es la contraseña pero permite ataque offline). Parte (a) es disponibilidad
operativa, sin vector de ataque.

## ISO/IEC 27001

- **A.5.37 Procedimientos operativos documentados** (a) — el orden de arranque no está descrito.
- **A.5.17 Información de autenticación** / **A.8.4 Acceso al código fuente** (b) — el verificador de
  credenciales puede acabar en el repo.
- **A.8.9 Gestión de la configuración** — la configuración sensible del pooler no está controlada.

## Qué debe asimilar el equipo

Las dependencias de arranque entre contenedores que comparten un secreto generado en runtime
(el hash SCRAM) necesitan un paso de inicialización explícito o un init-container; `depends_on` no
lo resuelve. Y todo fichero que PUEDA contener un secreto debe estar en `.gitignore` ANTES de que
exista su versión real — no confiar en que «nadie lo versionará».

## Criterio de cierre

(a) El README describe el orden de arranque (o un init-container lo automatiza) y un despliegue
desde cero levanta sin pasos manuales no descritos. (b) `git check-ignore
deploy/pgbouncer/userlist.txt` confirma que está ignorado.

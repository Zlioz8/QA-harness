## Qué está pasando

El `.env` del repositorio configura la conexión a la base de Moodle con
`MOODLE_DB_USER=postgres` —el **superusuario**— y `MOODLE_DB_NAME=zajunadb`. El propio `DEPLOY.md`
(§22) marca ambos: recomienda un rol de **solo lectura** dedicado (`reportes_ro`), y advierte que
el nombre correcto documentado es `zajuna`, no `zajunadb`. Verificado además contra el core de
esta máquina, donde el nombre real es un **tercero: `moodle`** — confirmando que el §19 del
documento («no asumas ninguno de los dos, verifica») es la instrucción correcta.

## Por qué es un riesgo

La aplicación solo necesita **leer** de Moodle (consultas de reportes y validación de tokens).
Conectarse con el superusuario `postgres` le da permisos de escritura y administración que no
usa: si la aplicación es comprometida (o una consulta se manipula), el alcance es toda la base de
datos de la plataforma, no solo lectura. Y un `MOODLE_DB_NAME` equivocado reproduce un fallo de
login ya documentado como resuelto.

## Recomendación de remediación

- Crear y usar un rol `reportes_ro` con únicamente `SELECT` sobre el esquema de Moodle (en el
  despliegue local de esta auditoría ya se creó como referencia).
- Fijar `MOODLE_DB_NAME` al nombre real del entorno destino, verificado con `psql`, no asumido.

## Verificación

```bash
# el rol de la app no puede escribir:
psql "host=... user=reportes_ro dbname=..." -c "CREATE TABLE x(i int);"   # debe fallar por permisos
```

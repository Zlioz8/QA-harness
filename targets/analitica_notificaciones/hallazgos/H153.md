## Qué está pasando

El archivo `.env` está versionado en el repositorio con **valores reales**, no marcadores:
`REPORTES_SECRET_KEY=zajuna_reportes_secure_2026_xK9mP` (la clave HS256 con la que
`api/auth.py` firma los tokens de sesión), `MOODLE_DB_PASSWORD=12345`, `DATABASE_PASSWORD` y
`POSTGRES_PASSWORD=reportes_2026_secret`.

`.gitignore` **sí** lista `.env` (línea 13), pero el archivo fue añadido al índice antes de esa
regla y sigue rastreado: `git ls-files` lo trae y `git status` sale limpio. Está *ignorado y a
la vez versionado* — el peor de los dos mundos, porque nadie lo nota. gitleaks lo confirma sobre
la **historia completa** (`--all`): la clave y las contraseñas viven en todos los clones para
siempre, aunque se borren del árbol.

El propio `DEPLOY.md` del equipo lo señala en su §22 como riesgo. Aquí se eleva a hallazgo con
evidencia y severidad porque la clave HS256 es la credencial más sensible del sistema.

## Por qué es un riesgo

Quien tenga `REPORTES_SECRET_KEY` puede **forjar un JWT válido para cualquier usuario**, incluido
un administrador: `get_current_user` solo verifica la firma HS256 con esa clave. No hace falta
robar una sesión; se fabrica. Las contraseñas de base de datos versionadas amplían el alcance a
la Control DB y, con el superusuario `postgres` (ver §3.10), a la base de Moodle.

## Recomendación de remediación

- Rotar **ya** `REPORTES_SECRET_KEY` (`openssl rand -hex 32`) y todas las contraseñas del `.env`.
- `git rm --cached .env` y confirmar; el archivo se queda solo en disco. Publicar un
  `.env.example` con las claves y valores VACÍOS (ver §3.8).
- Purgar el secreto de la historia (git filter-repo) o, más realista, tratar toda credencial que
  haya estado en la historia como comprometida y rotada.

## Verificación

```bash
git clone <repo> /tmp/an-limpio && cd /tmp/an-limpio
git ls-files | grep -q '^\.env$' && echo "TODAVÍA versionado" || echo "OK: fuera del índice"
```

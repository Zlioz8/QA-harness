## Qué está pasando

Tras desplegar siguiendo el §10 de `DEPLOY.md`, quedan servibles por HTTP **sin autenticación**
varios ficheros que no son páginas de la aplicación. Comprobado contra el despliegue, leyendo el
cuerpo devuelto y no solo el código de estado:

| Ruta | Devuelve |
|---|---|
| `/local/slider_form/db/migrations/001_saved_filters.sql` | 901 B — el DDL real |
| `/local/slider_form/db/migrations/007_envios2_verify.sql` | el DDL real |
| `/local/slider_form/README.md` | 6.644 B — el README |
| `/local/slider_form/docs/DESPLIEGUE_PREPROD.md` | el documento de preproducción |
| `/local/slider_form/docs/LOGIC_SEGMENTED.md` | la lógica de segmentación |
| `/local/slider_form/docs/Cuerpo_Correo.html` | 41.336 B — la plantilla del correo |

La causa es doble y ninguna mitad es culpa de la otra: el §10.1 obliga a copiar
`db/migrations/*.sql` y `docs/Cuerpo_Correo.html` al servidor (los necesita en tiempo de
ejecución y para aplicarlos con `psql`), y el `nginx` de la plataforma no restringe ninguna
extensión salvo `.git`, `.env`, `.htaccess`, `frontcmd.(zip|rar)` y `phpinfo.php`.

Nota de método, porque es fácil equivocarse aquí: **`prueba.html` NO está expuesto**. Devuelve
200, pero el cuerpo es la portada institucional que `try_files` sirve para cualquier ruta
inexistente. La exclusión de §10.1 funcionó. Comprobarlo por código de estado habría producido un
hallazgo falso — y el propio `DEPLOY.md` §10.1 propone justo esa comprobación (`esperado: 404`),
que sobre este `nginx` no distingue.

### Confirmado en navegador (no solo con `curl`)

Se repitió la comprobación con un navegador real contra el despliegue local, **sin sesión
iniciada**. No son redirecciones ni la portada: el navegador **descarga los ficheros**, y
coinciden byte a byte con los del repositorio.

| Fichero | Navegador | `sha256` (16 primeros) descargado / repositorio |
|---|---|---|
| `db/migrations/001_saved_filters.sql` | descarga 901 B | `db5676cae457b140` / `db5676cae457b140` |
| `docs/DESPLIEGUE_PREPROD.md` | descarga 6.037 B | `6f58bce5fd0fa3a7` / `6f58bce5fd0fa3a7` |

Y en la misma sesión de navegador se confirmó el contraste: `prueba.html` devuelve la portada
institucional («LMS ZAJUNA- CMS»), no el fichero del plugin. La exclusión de §10.1 funcionó y las
alertas de ZAP sobre esa ruta son de la portada — que es lo que ya se había triajado.

## Por qué es un riesgo

Los `.sql` son los más relevantes: describen el esquema `midb` completo —nombres de tablas,
columnas, tipos, índices y los catálogos de 34 regionales y 118 centros— a cualquiera que
conozca la ruta, sin sesión. No es una brecha por sí sola, pero es reconocimiento gratuito para
quien prepare una: le dice exactamente qué buscar.

`DESPLIEGUE_PREPROD.md` se cruza con el §3.1: es el documento que instruye a incrustar la
contraseña de PostgreSQL en el código, y se publica sin autenticación. Descargado del despliegue, su línea 52 dice literalmente:

```
$password = '<CLAVE_DESARROLLO_NO_VERSIONAR>';   // ← LÍNEA 20: reemplazar por la clave de postgres de PRE-PROD
```

Hoy el valor es un marcador de posición —verificado uno a uno— así que no filtra ninguna
credencial. Lo que publica es el **procedimiento** para crear la fuga del §3.1, incluida la ruta
y el número de línea exactos.

La plantilla del correo y los `.md` son de bajo impacto y se listan por completitud.

## Recomendación de remediación

Dos capas:

1. **En el servidor web** (DevOps/Infra), negar las extensiones que nunca deben servirse bajo el
   árbol de Moodle:

```nginx
location ~* /local/.*\.(sql|md|ods|puml|mmd|bak|zip)$ { deny all; return 404; }
```

2. **En el repositorio** (Backend), ampliar la lista de exclusiones de §10.1 con `docs/*.md` y
   `README.md`, que hoy el comando de §10 sí copia aunque la tabla diga que no. Las migraciones
   `.sql` sí tienen que ir al servidor, así que esas dependen de la capa 1.

Y sustituir la comprobación de §10.1 por una que mire el contenido, no el estado:

```bash
curl -sk .../prueba.html | grep -q 'DOCTYPE html' && echo "ojo: comprobar el CUERPO, no el código"
```

## Qué está pasando

Tres pantallas del plugin —`send_logs.php`, `table_logs.php` y `ajax/export_envios.php`— leen las
columnas `estado` y `sent_at` de `midb.envios2`. **Ninguna de las trece migraciones del
repositorio las crea.**

Medido tras aplicar la secuencia completa de `db/migrations/` sobre este despliegue, `midb.envios2`
queda con exactamente seis columnas:

```
id | destinatario | asunto | body | created_at | cursos
```

`DEPLOY.md` §8.5 declara el hueco como supuesto no verificado y propone, «hasta que se confirme el DDL real con el equipo responsable del proceso de
envío», añadir `estado text NOT NULL DEFAULT 'pendiente'` y `sent_at timestamptz`.

**Esta auditoría puede cerrar esa pregunta abierta con evidencia.** El mismo esquema `midb` de la
base de la plataforma contiene una tabla predecesora, `midb.envios1`, que preexiste al despliegue
y tiene 127 filas reales. Su definición incluye ambas columnas, y `estado` **no es `text`**:

```
estado  → tipo enumerado midb.env_estado
          valores: pendiente, en_proceso, enviado, fallo, cancelado
sent_at → timestamp with time zone
```

`midb.envios1` trae además `scheduled_at`, `updated_at`, `retry_count`, `last_error` y
`next_retry_at`, y la acompaña `midb.envios_log` (918 filas) con el rastro de eventos por envío.

## Por qué es un riesgo

Dos consecuencias distintas.

**Operativa inmediata:** un despliegue hecho solo con lo que trae el repositorio deja el historial
de envíos roto. `segmented.php` encola correos, pero `send_logs.php` responde
`SQLSTATE[42703]: Undefined column: column "estado" does not exist`. El usuario ve una pantalla
de error sin relación aparente con lo que acaba de hacer.

**Sobre el contrato entre componentes, que es lo más caro:** el consumidor real de la cola espera
un enumerado de cinco estados, y el parche que sugiere §8.5 crearía un `text` libre con dos
valores conocidos. Si alguien aplica ese parche en un entorno donde el proceso de envío sí corre,
el proceso escribirá `en_proceso`, `fallo` o `cancelado` en una columna que el plugin no espera, y
la validación que el enumerado daba gratis desaparece.

Esta auditoría **no aplicó el parche** precisamente por eso: habría medido una reconstrucción del
laboratorio en vez del sistema.

## Confirmado en ejecución, con dos errores distintos separados

Recorrido con una cuenta real con `:view` sobre el despliegue local:

| Pantalla | Resultado |
|---|---|
| `send_logs.php` | **404** · `Excepción - SQLSTATE[42703]: Undefined column: 7 ERROR: no existe la columna «estado» LINE 3: COUNT(*) FILTER (WHERE estado = 'enviado')` |
| `table_logs.php?asunto=…&created_at=…` | **404** · mismo `SQLSTATE[42703]` |

La segunda fila requiere una precisión de método. `table_logs.php` exige **dos** parámetros obligatorios (`asunto` y `created_at`, líneas 27-28) y la primera versión
del guion de carga solo pasaba uno: el endpoint devolvía `404 · «Un parámetro necesario
(created_at) faltaba»`, un error de la prueba que **tapaba** el error real. Con los dos
parámetros correctos aparece el `42703`, que es el defecto del proyecto.

El usuario ve una excepción de base de datos con el fragmento de SQL a la vista — que además es
divulgación de estructura interna, no solo un fallo funcional.

## Recomendación de remediación

1. Confirmar con el equipo dueño del proceso de envío si `midb.envios1` es el contrato vigente y
   `envios2` su sucesora, o si son dos colas distintas. Es una pregunta de una conversación.
2. Según la respuesta, **añadir una migración 014** que cree las columnas con el tipo real:

```sql
-- si el contrato es el de envios1:
ALTER TABLE midb.envios2
  ADD COLUMN IF NOT EXISTS estado  midb.env_estado NOT NULL DEFAULT 'pendiente',
  ADD COLUMN IF NOT EXISTS sent_at timestamptz;
CREATE INDEX IF NOT EXISTS envios2_estado_idx ON midb.envios2 (estado);
```

3. Actualizar §8.5 de `DEPLOY.md`: hoy plantea una pregunta abierta que ya tiene respuesta
   observable en la propia base.

## Verificación

```sql
SELECT column_name, data_type, udt_name FROM information_schema.columns
 WHERE table_schema='midb' AND table_name='envios2' AND column_name IN ('estado','sent_at');
-- estado debe salir con udt_name = env_estado
```
Y en la aplicación: `send_logs.php` debe cargar sin error con una sesión con `:view`.
